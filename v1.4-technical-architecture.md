# v1.4 — Technical Architecture

## What Competitors Actually Use (From Page Source Analysis)

| Competitor | Framework | Hosting | Schema | JS Payload | Analytics |
|------------|-----------|---------|--------|------------|-----------|
| HustleCalcs | Vanilla HTML/CSS/JS | Static (Netlify/Vercel likely) | None (visual breadcrumbs only) | Minimal (15-30KB) | None visible in page source |
| CalculatorCove | Static HTML + CSS + JS | Cloudflare | Full (WebApplication + BreadcrumbList + FAQPage) | Minimal + GA4 | GA4 (`G-XPMR577VM1`) |
| OnlineCalcAI | Next.js/SSR (inferred) | Unknown | None visible | Moderate | Unknown |
| SaaSMetricsCalculator | Static HTML, React SPA | Unknown | None | React bundle | Unknown |

**Key architectural insight**: The most successful competitor by traffic (HustleCalcs) uses the simplest tech stack possible — no framework, no SSR, no analytics scripts. CalculatorCove, with the deepest content and best SEO, uses static HTML + Cloudflare. **A framework is not required to succeed in this market.** The choice of Next.js is a developer preference, not a competitive necessity.

**Implications for our architecture**:
- Our config-driven Next.js SSG approach must NOT add unnecessary JS bloat compared to HustleCalcs' 15-30KB pages
- CalculatorCove's full schema implementation is the minimum bar — not optional
- HustleCalcs' lack of analytics scripts is intentional (privacy, speed) — consider edge analytics only
- The embed widget architecture is something NO competitor has — it's our primary technical differentiator

**Claim from v1.3**: "Ad revenue can hit $1,000/month at 50K sessions with $20 RPM."
- **Corrected**: At $8-15 RPM (realistic), need 80K+ sessions. Architectural implication: must support scale without performance degradation. HustleCalcs' vanilla HTML loads in <500ms — our Next.js SSG must match this.

**Claim from v1.3**: "Freemium conversion of 1-2% is realistic (corrected)."
- **Architectural implication**: The freemium flow must be frictionless (0-click upgrades, no account-required for basic use). Account creation should be async/optional — only required for Pro features export.

**Claim from v1.3**: "Mediavine requires 50K sessions."
- **Corrected**: Mediavine Journey now requires 1K sessions (75% rev share). Full Mediavine requires $5K/yr ad revenue. Architectural implication: ad slots must be designed for easy integration with multiple networks over the site's lifetime.

## Stack Decision

| Layer | Choice | Rationale |
|-------|--------|-----------|
| Framework | Next.js 16 (App Router) | SSG-first, Server Components, best SEO framework for content-driven tools |
| Language | TypeScript 5.x | Type safety across config, calculation engine, and components |
| Styling | Tailwind CSS v4 + shadcn/ui | Consistent design, tree-shakeable, zero-runtime CSS |
| Hosting | Vercel (Pro once revenue starts) | Free tier for MVP, seamless Next.js integration, edge CDN |
| Analytics | PostHog (self-host or cloud) | Privacy-respecting, event-based, better than GA4 for tool analytics |
| Payment | Stripe + Polar.sh | Polar.sh is open-source-first, great for PLG; Stripe as fallback |
| Database | SQLite (Turso) or PostgreSQL (Neon) | Turso for edge-reads of calculator config; Neon for user data |
| State | URL searchParams + React Context | URL is source of truth for calculator state (shareable by default) |

## Architecture: Configuration-Driven Generation

### Core Principle
Don't build 50 pages — build **1 page** that reads **50 configurations**.

```
webcalc/
├── calculators/
│   ├── config/               # JSON/YAML configs, one per calculator
│   │   ├── mrr-calculator.ts
│   │   ├── cac-calculator.ts
│   │   ├── ltv-calculator.ts
│   │   └── ...
│   ├── engine/                # Pure math functions, zero React dependency
│   │   ├── mrr.ts
│   │   ├── cac.ts
│   │   └── ...
│   └── ui/                    # Shared presentation components
│       ├── CalculatorShell.tsx
│       ├── ResultCard.tsx
│       ├── InputSlider.tsx
│       └── Chart.tsx
├── app/
│   ├── [category]/
│   │   └── [slug]/
│   │       └── page.tsx       # Single dynamic route for all calculators
│   ├── layout.tsx
│   └── page.tsx               # Landing / category hub
├── lib/
│   ├── registry.ts            # Calculator config loader
│   └── seo.ts                 # Metadata + JSON-LD generators
└── public/
    └── calculators/           # OG images, static assets per calc
```

### Calculator Config Schema
```typescript
interface CalculatorConfig {
  slug: string
  category: 'saas-metrics' | 'business-ops' | 'marketing' | 'finance'
  meta: {
    title: string           // "MRR Calculator 2026" — exact match keyword
    description: string     // 150-160 chars for meta description
    keywords: string[]      // related long-tail keywords
  }
  inputs: CalculatorInput[]
  outputs: CalculatorOutput[]
  engine: {
    formula: string         // human-readable formula explanation
    // fn is imported from engine/ module automatically
  }
  charts?: ChartConfig[]
  premium?: boolean         // whether this calc requires Pro for full output
}
```

## Rendering Strategy

| Page Type | Strategy | Rationale |
|-----------|----------|-----------|
| Calculator pages | SSG (`generateStaticParams`) | Pre-built HTML at build time, CDN-served, sub-100ms TTFB |
| Landing / category hub | SSG + ISR (revalidate: 3600) | Content updates propagate within an hour |
| Blog / supporting content | SSG + ISR | Fresh SEO content without rebuild |
| User dashboard | Dynamic (SSR) | Authenticated, user-specific data |
| API routes (stripe/pro) | Edge Functions | Low-latency payment/auth |

**Build time estimate**: 50 calculators × ~1s per page = ~50s build time. Scales linearly. CalculatorCove has 700+ static HTML pages with no build pipeline — they add pages manually. Our config-driven approach is more scalable but requires CI/CD discipline. At 200 calculators, expect ~3.5 min build time (ISR mitigates this for production).

## Freemium Architecture

- All calculators fully functional
- Basic results displayed instantly
- 3-5 calculations saved in localStorage

- Auth via NextAuth.js (Google + email magic link)

- Feature flags via middleware: check subscription on /pro routes
- Ad display: dynamically insert/remove ad units based on user tier

## Calculator Engine Design

### Pure Domain Modules
```
calculators/engine/mrr.ts
— fn calculateMRR(params): pure function, no side effects
— fn projectMRR(params, months): compounding projection
— fn churnImpact(params): churn sensitivity analysis
```
- No React, no fetch, no side effects
- 100% unit-testable
- Can be reused server-side for OG image generation
- Can be extracted to a standalone npm package for API/embed customers

### Formula Reference
Every calculator stores its formula as both code and human-readable text:
```typescript
export function calculateMRR(params: MRRParams): MRRResult {
  // MRR = number_of_customers × average_revenue_per_customer
  const mrr = params.customers * params.arpu
  // Net New MRR = new_customers × arpu + expansion - churn
  const netNew = params.newCustomers * params.arpu - params.churnedCustomers * params.arpu
  return { mrr, netNew, projectedArr: mrr * 12 }
}
```

## Development Workflow

### Adding a New Calculator
1. Create config in `calculators/config/new-calc.ts`
2. Create pure engine in `calculators/engine/new-calc.ts`
3. Add to registry in `lib/registry.ts`
4. Run `npm run generate` → SSG builds all pages
5. Automated: schema validation, broken link check, OG image generation

### CI/CD
- GitHub → Vercel (auto-deploy on main)
- Preview deployments for branch PRs
- Lighthouse CI check on every PR
- `tsc --noEmit` + `biome check` in CI

## Key Technical Decisions (To Question in v1.5)

1. Configuration-driven generation over hand-built pages — is the config schema flexible enough for all 50 calculator types?
2. URL-driven state — will extremely complex calculators with dozens of inputs overflow the URL (browser URL length limits ~2K chars)?
3. SSG at scale — is 50→200 calculators going to blow up build time unacceptably?
4. Freemium via account — will the account wall kill conversion for a tool that works fine without it?
5. PostHog over GA4 — is the event-based model worth the lack of Google Search Console integration?
