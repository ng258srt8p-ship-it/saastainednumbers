# Fix `npm run dev` Dev Server Failure — Diagnostic & Repair Plan

> **For Hermes:** Complete Diagnosis first (Task 1) to identify the exact error, then execute the matching repair task.

**Goal:** `npm run dev` (Next.js 16.2.6, Turbopack) should start cleanly and serve every page with zero errors.

**Current state (as of investigation):**
- `npm run dev` starts Next.js 16.2.6 (Turbopack) in ~233ms
- All tested pages (homepage, pricing, blog, calculator, dashboard, category) return HTTP 200
- No errors visible in dev server log
- One deprecation warning: middleware → proxy convention

**Possible failure modes (user-dependent):**
- A. Port conflict (EADDRINUSE) — another server on port 3000
- B. Turbopack cache corruption — stale cache from previous errors
- C. Node.js version mismatch — missing or incompatible dependency
- D. `.next` build artifact interference — stale production build
- E. Env var missing — `.env.local` not present

---
## Task 1: Diagnose the Exact Failure

**Objective:** Reproduce the exact error the user sees and identify which failure mode applies.

**Files:**
- Read: `package.json` (scripts section)
- Read: `next.config.js` or `next.config.ts`
- Read: `.env.local` (check presence)
- Read: `middleware.ts`
- Read: `node_modules/.package-lock.json` versions

### Step 1: Check basic requirements

```bash
node --version
npm --version
ls -la .env.local 2>/dev/null || echo "NO .env.local"
cat .env.local 2>/dev/null | grep -v PASSWORD | head -5
```

Expected: Node >= 18.18. `.env.local` with: `AUTH_SECRET`, `AUTH_GOOGLE_ID`, `AUTH_GOOGLE_SECRET`, `AUTH_RESEND_KEY`, `DATABASE_URL`, `NEXT_PUBLIC_POSTHOG_KEY`, `NEXT_PUBLIC_POSTHOG_HOST`, `NEXT_PUBLIC_ETHICAL_ADS_ID`, `NEXT_PUBLIC_ADSENSE_ID`, `NEXT_PUBLIC_BASE_URL`.

### Step 2: Kill conflicting servers

```bash
lsof -i :3000
# If running:
kill -9 <PID>
```

If port 3000 is in use, `npm run dev` will fail with `EADDRINUSE`. Fix: kill the process or use `--port` flag.

### Step 3: Run dev and capture full output

```bash
npx next dev > /tmp/next-dev-full.log 2>&1 &
sleep 15
cat /tmp/next-dev-full.log
```

Expected output includes: `▲ Next.js 16.2.6 (Turbopack)`, `✓ Ready in <time>ms`.

### Step 4: Check for compilation errors

```bash
# Hit pages that are likely to fail
for url in / /pricing /blog /revenue/mrr-calculator /dashboard /churn/churn-rate-calculator; do
  echo -n "$url → "
  curl -sL -o /dev/null -w "%{http_code}" "http://localhost:3000$url" 2>/dev/null || echo "FAIL"
done
```

All should return 200.

### Step 5: Check the dev log for errors

```bash
grep -i "error\|fail\|unhandled" /tmp/next-dev-full.log || echo "No errors found"
```

## Task 2: Fix Port Conflict (Failure Mode A)

**Objective:** Ensure `npm run dev` doesn't fail because port 3000 is occupied.

**Files:**
- Modify: `package.json` (dev script)

### Step 1: Update dev script to auto-select available port

In `package.json`, change:
```json
  "scripts": {
    "dev": "next dev",
```
to:
```json
  "scripts": {
    "dev": "next dev -p 3000 || next dev -p 3001 || next dev -p 3002",
```
Or better, detect and kill the conflicting process automatically via a pre-dev script.

### Step 2: Test

```bash
# Simulate conflict
npx serve -l 3000 &
npm run dev 2>&1 | head -20
# Should use alternate port or complain differently
kill %1
```

## Task 3: Clear Turbopack Cache (Failure Mode B)

**Objective:** Eliminate stale corrupt Turbopack compilation artifacts.

**Files:**
- Delete: `.next/cache/` (Turbopack cache directory)
- Delete: `node_modules/.cache/` (Next.js build cache)

### Step 1: Clear caches

```bash
# Clear Next.js / Turbopack build cache
rm -rf .next/cache
rm -rf node_modules/.cache

# Re-run dev
npx next dev
```

### Step 2: If still failing, deeper clean

```bash
# Nuclear option — full clean rebuild
rm -rf .next
npm run dev
```

In `proxy.ts`, change any `export function middleware` to `export function proxy` if needed (Next.js proxy.ts convention uses the same export name as middleware.ts but the file is detected by filename).

## Risks & Open Questions

1. **Could not reproduce the error** during investigation. All pages load correctly via dev server. The failure may be environment-specific (Node version, port conflict, stale node_modules).
2. **Middleware → Proxy migration** (Task 4) is safe — Next.js 16.x supports both, but deprecation warnings can cause confusion when users scan logs for actual errors.
3. **Turbopack cache** is the most likely culprit if the error appeared after multiple build/restart cycles. The cache at `.next/cache/` can hold stale compiled modules that fail on re-compilation.
4. **Dashboard page** previously blocked in dev by Turbopack cache — if the error is on /dashboard only, clearing cache (Task 3) is the fix.
5. **If none of these apply**, provide the user with the full dev server log output for further diagnosis.
