# Canvas Page White Bar — Plan

> **Rule: Every claim in this plan must be verified with Playwright before the next step. If the measurement contradicts the claim, update the plan before proceeding. Never implement based on an assumption — measure first.**

**Goal:** Remove the visible white bar at the top of `/canvas/` without breaking any other page.

**Ground truth:** Only Playwright pixel measurements count as evidence. CSS analysis, DOM inspection, and visual inspection by the agent are all secondary — they can mislead.

## Phase 0: Investigation (Playwright MUST run first)

Before any code changes, run these four Playwright investigations. Each produces a verdict that determines the next step.

### Investigation 0.1: Map the actual pixel colors

### Investigation 0.2: Identify the "bar" color precisely

Run a pixel-read script across the horizontal strip from y=0 to y=100 at intervals of 2px, at x=320 (sidebar column center) and x=960 (workspace column center). Plot the RGB deltas between consecutive y-samples.

**Script:**

```javascript
const { PNG } = require('pngjs');
const fs = require('fs');

function analyze(filename, label) {
  const data = PNG.sync.read(fs.readFileSync(filename));
  const get = (x, y) => { const i = (y * data.width + x) * 4; return [data.data[i], data.data[i+1], data.data[i+2]]; };
  console.log(`=== ${label} ===`);
  for (let y = 0; y < 100; y += 4) {
    const [r, g, b] = get(320, y);  // sidebar column
    const [r2, g2, b2] = get(960, y);  // workspace column
    console.log(`y=${y.toString().padStart(2)}  sidebar=[${[r,g,b].join(',')}]  workspace=[${[r2,g2,b2].join(',')}]`);
  }
}
analyze('/tmp/canvas-top-light.png', 'LIGHT MODE');
analyze('/tmp/canvas-top-dark.png', 'DARK MODE');
```

**What to look for:** Any y where the RGB value changes by more than 15 points from the previous sample indicates a visible boundary/bar.

### Investigation 0.3: Verify Safari height issue

Reproduce the Safari bug where canvas height was 3989px instead of 100vh.

**Check in Chromium too** — does `100vh` compute correctly, or is there a CSS cascade issue?

```javascript
const box = await page.locator('.flex.h-screen').boundingBox();
```

If clientH !== scrollH, something inside the canvas is expanding beyond the container despite `overflow-hidden`.

## Phase 1: Form Hypotheses (based on measurements, not guesses)

After Investigation 0.1-0.4, you'll know:

1. **Is the bar real?** (pixel delta > 15 threshold) → If no, the issue might be a Safari-specific rendering bug or a FOUC.
2. **Where exactly is the bar?** y-range where RGB changes → This identifies the exact elements involved.
3. **What color is the bar?** The specific RGB → Matches to a Tailwind color class → Identifies which element's background is showing.
4. **Is it canvas-specific?** Compare with regular page measurement.

Based on the FOUR possible outcomes, pick ONE hypothesis:

| If measurements show... | Hypothesis | Action |
|---|---|---|
| **A.** Pixel delta at nav/content boundary < 15, but user reports a bar | The issue is a flash-of-unstyled-content (FOUT/FOUC) during page load. The white bar appears before CSS loads. | Fix: Add `body { background: ... }` to preload styles, or SSR the correct theme class |
| **B.** Pixel delta > 15 at y ~66 (the padding area to sidebar transition) | The 66px padding area has a different color than the sidebar below. The canvas container bg doesn't match the sidebar bg perfectly. | Fix: Make the canvas container transparent and push padding to children (Option A from previous) |
| **C.** Pixel delta > 15 at y ~16 (the nav top-4 gap to nav pill) | The `top-4` gap shows the body background (white) above the pill. | Fix: Remove `top-4` gap (set to `top-0`) |
| **D.** Pixel delta > 15 across the entire top 66px (entire padding area vs content below) | The canvas container `bg-white dark:bg-gray-800` doesn't match the body `bg-white dark:bg-gray-950` or the workspace area. | Fix: Change canvas container bg to match body or remove bg entirely |

## Phase 2: Implement ONE fix (based on the measured hypothesis)

Only implement the fix that matches the measured hypothesis. Do NOT implement all options.

For each fix option, the implementation is:

### Fix A: FOUC/FOUT fix

If the white bar is a flash during page load:
1. Add an inline `<style>` block in `app/layout.tsx` that sets `body` background to the correct theme before any CSS loads
2. OR remove the `dark` class from the SSR HTML and let JS set it after hydration (avoids theme flash)
3. Test with slow network throttling

### Fix B: Padding to children (Option A)

If the 66px padding area has a mismatched color:
1. `app/canvas/page.tsx`: Remove `bg-*` and `paddingTop` from canvas container. Just `<div class="flex h-screen overflow-hidden" style="height:100vh">`
2. `components/canvas/CalculatorCatalog.tsx`: Add `pt-[66px]` to the `<aside>` element
3. `components/canvas/CalculatorWorkspace.tsx`: Change `p-6` to `px-6 pb-6 pt-[66px]` on the workspace `<main>`

### Fix C: Remove nav top gap

If the `top-4` gap shows body white:
1. `components/Nav.tsx`: Change `top-4` to `top-0` WITHOUT adding any background
2. Verify the floating nav appearance is still acceptable

### Fix D: Match canvas bg to body

If the canvas bg mismatches the body/workspace:
1. `app/canvas/page.tsx`: Change canvas container bg to `bg-white dark:bg-gray-950` (matches body)
2. OR make the canvas container transparent (`bg-transparent`)
