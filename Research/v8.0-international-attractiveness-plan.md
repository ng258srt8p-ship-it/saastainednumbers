## 1. Why This Matters

OnlineCalcAI generates **65K sessions/month** and ~**$10K/month** with 206 calculators × 30 languages = **6,180 indexed pages**. Their multi-language strategy multiplied indexed pages by 30×, creating a proportional traffic multiplier. Our current position:

| Metric | OnlineCalcAI | Us | Gap |
|--------|-------------|----|-----|
| Languages | 30 | 1 (EN) | 30× |
| Indexed pages | ~6,180 | ~219 | 28× |
| Non-English traffic | ~60% | ~0% | — |
| Sessions/month | ~65K | ~0 (pre-index) | — |

Every prior research doc (v1.2, v1.3, v1.5, v1.9, v1.10, v2.1, v3.0) names multi-language as a **top-3 priority** starting month 3-6. We are past that window — 75 calculators exist, but none have translated content.

### ROI Estimate

| Phase | Effort | Traffic Impact | Timeline |
|-------|--------|--------------|----------|
| Quick wins (locale switcher, formatting) | 1-2 days | Low (UX, not indexed) | Week 1 |
| SEO infrastructure (hreflang, sitemap, lang attr) | 2-3 days | Medium (Google signals) | Week 1-2 |
| Calculator content translation (5 lang × 75 calcs) | 4-6 weeks | High (5× indexed pages) | Weeks 3-8 |
| Blog translation pipeline | 2 weeks | Medium (content marketing) | Weeks 6-8 |

**Conservative**: 5 languages × 75 calculators = 375 additional indexed pages. At OnlineCalcAI's ~0.1 sessions/page/day ratio for generic calculators, this could add 35-40 sessions/day for our SaaS-focused content (lower due to niche audience). Realistic: **20-30% traffic uplift** from non-English markets within 3 months of deployment.

## 2. Current State Audit

### What Works (Already in Place)
- **6 locale files** (EN, ES, DE, PT, FR, JA) with correct structure — currently hold only 3 nav keys each
- **Cookie-based locale detection** in `middleware.ts` with Accept-Language fallback
- **Server-side translation loader** (`lib/getTranslations.ts`) works correctly
- **`/api/locale` endpoint** for programmatic locale switching exists

### What's Missing — By Severity

#### Critical (blocks everything)
| Gap | Details |
|-----|---------|
| `CalculatorConfig` has zero i18n support | Input labels, output labels, meta title/description, content.intro, content.howToUse, content.formulaExplanation, content.benchmarks, content.faq — all hardcoded `string` fields. Schema at `calculators/config/calculator-schema.ts` needs per-locale key structure. |
| No locale routing structure | No `/de/revenue/mrr-calculator` paths. `lib/i18n.ts` `getLocaleFromPath()` is dead code. All 75 calculator routes are English-only. |
| `<html lang="en">` is hardcoded | Should reflect user's locale cookie. Currently declares English for all visitors regardless of language. |

#### High (needed before launch)
| Gap | Details |
|-----|---------|
| No hreflang tags | Zero `<link rel="alternate" hreflang="es" ...>` in layout or any page metadata. Google cannot associate language versions. |
| No localized sitemap | Sitemap lists only English URLs. No `<xhtml:link rel="alternate">` entries. |
| No locale switcher UI | Users cannot change language. 6-language support is invisible. |
| Number/currency formatting hardcoded to `en-US` | `Intl.NumberFormat("en-US")` in 6+ components (ResultCard, DeltaBadge, LiveCounter, DashboardWidget, DashboardTotalWidget, ComparisonChart) and `"$"` prefix in InputSlider. German users see `$1,234.56` instead of `1.234,56 $`. |

#### Medium (important for quality)
| Gap | Details |
|-----|---------|
| Client-side i18n hook (`useLocale.ts`) is dead code | Zero callers. Components cannot reactively re-render on locale change. |
| OG images are English-only | `/api/og` always renders English text regardless of locale. |
| Blog content is English-only | No locale subdirectories under `content/blog/`. |
| Pricing page text is hardcoded English | "$0 forever", "Everything is Free" — not in translation files. |
| All meta descriptions, keywords are English-only | No per-locale `generateMetadata()`. |

#### Low (nice-to-have)
| Gap | Details |
|-----|---------|
| Date formatting not locale-aware | Blog dates rendered verbatim from frontmatter. |
| Calculator defaults are USD-centric | No regional defaults (EUR for DE, JPY for JP, etc.). |
| `lib/i18n.ts` dead code | `getLocaleFromPath()` written for path-based routing that was never built. Confusing to future developers. |

## 3. Phased Implementation Plan

### Phase 0: Foundation (Week 1) — Quick Wins, Zero Content Translation

These changes improve UX for non-English visitors immediately without requiring any translated content.

#### P0.1 — Locale Switcher UI
- Create `components/LocaleSwitcher.tsx` — dropdown/flag selector calling `/api/locale?locale=xx`
- Add to `Nav.tsx` and `MobileNav.tsx`
- Wire to existing `/api/locale/route.ts`

#### P0.2 — Dynamic `<html lang>` Attribute
- Root layout reads `locale` cookie (server-side via `cookies()`)
- `<html lang={locale}>` instead of hardcoded `lang="en"`

#### P0.3 — Number/Currency Formatting Per Locale
- Create `lib/formatNumber.ts` utility: `formatCurrency(value, locale)`, `formatPercent(value, locale)`, `formatNumber(value, locale)`
- Replace all `Intl.NumberFormat("en-US")` calls across 6+ components
- Replace hardcoded `"$"` prefix in `InputSlider.tsx` with locale-aware currency symbol

#### P0.4 — Wire `useLocale.ts` to Client Components (Optional)
- Make the dead `useLocale.ts` hook reactive
- Or remove it entirely if server-side approach (`getTranslations.ts`) covers all needs

### Phase 1: SEO Infrastructure (Week 1-2) — Tell Google About Our Languages

These changes make non-English pages discoverable and properly attributed in search engines.

#### P1.1 — Hreflang Tags in Layout
- Add `alternates.languages` to root layout metadata
- Generate `<link rel="alternate" hreflang="es" href="...">` for all 6 locales on every page
- Pattern: `https://saastainednumbers.com/${locale}/${category}/${slug}`

#### P1.2 — Localized Sitemap
- Update `app/sitemap.ts` to generate locale-prefixed URLs for each of the 6 languages
- Add `<xhtml:link rel="alternate" hreflang="xx" href="...">` entries for each URL
- Total sitemap grows from ~219 URLs to ~1,314 URLs (219 × 6)

#### P1.3 — Locale-Prefixed Routing
- Implement proper locale routing: `middleware.ts` rewrites `/revenue/mrr-calculator` → `/en/revenue/mrr-calculator` and handles `/de/revenue/mrr-calculator` by stripping the prefix and setting the cookie
- Update internal links (breadcrumbs, related calculators, nav) to preserve locale prefix
- **Decision point**: Subdomain (`de.saastainednumbers.com`) vs path prefix (`/de/revenue/`)

#### P1.4 — Canonical + Alternate Metadata Per Page
- Update `generateMetadata()` in `lib/seo.ts` to accept locale parameter
- Generate per-locale canonicals and alternates
- Update all page metadata exports

### Phase 2: Content Architecture (Week 2-3) — Make Calculator Data Translatable

This is the foundational engineering work that unlocks all content translation.

#### P2.1 — Refactor `CalculatorConfig` Schema
- Add optional per-locale fields to `CalculatorConfig`:
  ```ts
  interface CalculatorConfig {
    // Existing fields (default/fallback = English)
    meta: { title: string; description: string; keywords: string[] };
    inputs: CalculatorInput[];
    outputs: CalculatorOutput[];
    content: CalculatorContent;

    // New: per-locale overrides
    locales?: Partial<Record<SupportedLocale, {
      meta?: { title?: string; description?: string; keywords?: string[] };
      inputs?: { id: string; label?: string }[];
      outputs?: { id: string; label?: string }[];
      content?: {
        intro?: string;
        howToUse?: string;
        formulaExplanation?: string;
        benchmarks?: Benchmark[];
        faq?: { question: string; answer: string }[];
      };
    }>>;
  }
  ```
- Alternatively: create per-locale config files: `calculators/config/mrr-calculator.es.ts`, etc.

**Recommendation**: Inline locale overrides in the main config. Keeps everything in one file per calculator; avoids 75×5 extra files. Fallback to English defaults when locale override is missing.

#### P2.2 — Update `lib/seo.ts` for Locale-Aware Metadata
- `generateMetadata()` accepts `locale` parameter
- Generates locale-specific `<title>`, `<meta name="description">`, OG tags, JSON-LD
- JSON-LD text updates: breadcrumb labels ("Home" → "Inicio"), WebApplication name, FAQ questions

#### P2.3 — Calculator Content Renderer Locale Support
- `app/[category]/[slug]/layout.tsx` reads locale and selects appropriate content
- FAQ accordion, editorial sections, benchmark tables populate from locale overrides
- Fall back to English when locale content is missing

#### P2.4 — Translation Key System for Non-Calculator UI
- Add translation keys to `i18n/${locale}/common.json` for all hardcoded UI strings:
  - Footer links, category names, "Home", "Related Calculators", "How to Use", "Formula", "Benchmarks", "FAQ"
  - Search placeholder, "No signup. No email. No catch.", "Browse All Calculators"
  - Pricing page: "Everything is Free", "No subscriptions, no paywalls"
  - Dashboard: "Add from calculators", "Executive Summary"
  - `FeedbackWidget.tsx`: "Was this helpful?", "Yes", "No"
  - `EmailCapture.tsx`: form labels, button, success/error messages
  - "Page Not Found", "Calculator Not Found", "Go Home"
  - Category names: "Revenue", "Churn & Retention", "Growth & Efficiency", etc.

Target: ~80-100 keys covering ALL user-facing UI strings.

### Phase 3: Content Translation (Week 3-6) — Translate Everything

This is the highest-effort phase. Approach pragmatically — translate by SEO priority.

#### P3.1 — Priority Calculator Translation (Week 3-4)
Translate the **top 20 calculators** that drive the most search traffic:
- **Revenue**: MRR, ARR, ARPU, LTV, NRR
- **Churn**: Churn Rate, NPS, Customer Health, Engagement
- **Growth**: CAC, Quick Ratio, Magic Number, Rule of 40
- **Unit Econ**: Gross Margin, Contribution Margin, Payback, Burn Rate
- **AI Cost**: Claude API, ChatGPT API, Model Comparison

For each: translate `meta.title`, `meta.description`, `meta.keywords`, input/output labels, `content.intro`, `content.faq` (questions + answers). Total: ~80-100 words per calculator × 20 calculators × 5 languages = ~8,000-10,000 translated words.

**Approach options**:
- **A: Professional translation** (~$0.10/word = ~$1,000 total for 20 calculators) — highest quality, best SEO
- **B: Machine translation + human review** (~$0.02/word + $50/hr review = ~$500) — good quality
- **C: Machine translation only** (free via DeepL API/Google Translate) — acceptable for MVP, risk of fluency issues

#### P3.2 — Remaining 55 Calculators (Week 4-6)
- Batch translate remaining calculators by category
- Focus on UI labels and meta first; expand to full content later
- Machine translation acceptable for longer editorial content (intro, how-to, formula)

#### P3.3 — Blog Translation Pipeline (Week 6)
- Set up locale subdirectories: `content/blog/es/`, `content/blog/de/`, etc.
- Translate top 5-10 blog posts as a starting point

## 4. Architecture Decisions

### Decision 1: Path Prefix vs Subdomain

| Option | Pros | Cons |
|--------|------|------|
| **Path prefix** (`/de/revenue/mrr-calculator`) | Same domain, all link equity consolidated, simpler hreflang, works with existing middleware | Requires URL rewrites in middleware |
| **Subdomain** (`de.saastainednumbers.com`) | Cleaner separation, easier to geo-target in GSC | Dilutes domain authority, requires DNS config, more complex hreflang |

**Recommendation**: Path prefix. Consolidates link authority on a single domain, works with our existing middleware, and is the pattern recommended by Google for multi-language sites.

### Decision 2: Inline Locale Overrides vs Separate Files

| Option | Pros | Cons |
|--------|------|------|
| **Inline in config** (`locales: { es: { meta: {...} } }`) | Single file per calculator, obvious fallback, less filesystem overhead | Larger config files, more complex type |
| **Separate files** (`mrr-calculator.es.ts`) | Clean separation, easier to parallelize translation, smaller files | 75×5 = 375 extra files, complex import logic |

**Recommendation**: Inline locale overrides for MVP. If the translation scope grows beyond 5 languages, migrate to separate files.

### Decision 3: Translation Management

| Option | Pros | Cons |
|--------|------|------|
| Manual JSON editing | No additional tooling, full control | Tedious, error-prone for 75 calculators |
| DeepL API bulk script | Fast, cheap, consistent | Requires API key, needs human review |
| Crowdin / Lokalise | Professional translation workflow, collaboration | Monthly cost, overkill for our scale |

**Recommendation**: Build a Node.js script that extracts all translatable strings from calculator configs into a flat JSON per-language file, then imports the translations back. Use DeepL API for initial pass, then human review for the top 20 calculators.

## 6. Risks & Mitigations

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| Machine translation fluency issues for Japanese | Medium | High | Professional review for JA; target only EN/ES/DE/PT/FR first |
| Duplicate content penalty if translations are too thin | Low | Medium | Canonical + hreflang correct prevents this; Google knows these are translations |
| Redirect chain issues from new URL structure | Low | High | Careful middleware implementation; test with `?redirect=0` |
| Translation management becomes a maintenance burden | Medium | Medium | Script-based approach; batch translations after English content stabilizes |
| Non-English pages don't rank because of domain authority | High | Medium | Accept longer timeline for non-English rankings; benefit from existing DA buildup |
