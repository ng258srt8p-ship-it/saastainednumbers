## Key Architecture Notes

1. **oMLX is paged SSD-only mode.** All KV cache data is stored on SSD via `PagedSSDCacheManager`. The in-memory PagedCacheManager holds only metadata (block indices, hashes). No actual cache data lives in RAM during idle periods.

2. **There is no hot cache.** The `hot_cache_max_size: 10GB` setting in settings.json is wired nowhere. It defaults to 0 (disabled). The "Memory X GB / Y GB" on the dashboard is a ProcessMemoryEnforcer budget estimate, not an actual managed cache.

3. **mlx-lm's BatchGenerator** handles in-memory KV cache during active inference (during forward passes). This is automatic and has no explicit upper bound.

4. **Context window:** The configured 524,288 (512K) token limit is well above what your 64GB RAM can physically hold for this model at 4-bit (~310K tokens practical max). Requests above ~310K will be rejected by the ProcessMemoryEnforcer.

## Claude Code Integration

Claude Code (`~/.claude/settings.json`) is configured to route all requests through oMLX:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://127.0.0.1:8000",
    "ANTHROPIC_API_KEY": "958659"
  },
  "model": "Qwen3.6-35B-A3B-4bit"
}
```

oMLX resolves `Qwen3.6-35B-A3B-4bit` to the default model (loaded on demand, unloaded when idle).

## Hermes Integration (optional)

Hermes config (`~/.hermes/config.yaml`) can be configured to use the same oMLX endpoint with a higher context_length (recommended: 524288, matching oMLX).
